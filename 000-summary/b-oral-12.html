078

先讲正确性，事务的 ACID：原子性、一致性、隔离性、持久性。其中隔离性是可以调节的，有四个级别：读未提交会读到别人没提交的数据，也就是脏读；读已提交解决了脏读，但同一事务里两次读的结果可能不同，也就是不可重复读；可重复读是 InnoDB 的默认级别；串行化最严格，性能最差。

082

隔离级别怎么实现？如果全靠加锁，读写会互相阻塞。InnoDB 用 MVCC：每一行有隐藏的事务 ID 和回滚指针，指向 undo log 里的旧版本，形成一条版本链。读的时候生成一个 ReadView，沿着版本链找到自己可见的那个版本，于是读不阻塞写。读已提交是每条语句生成一个新的 ReadView，可重复读是整个事务只用第一次生成的那个，这就是两者的本质区别。

081

MVCC 用到了 undo log，这就引出三种日志：undo log 用于回滚和 MVCC，保证原子性；redo log 是 InnoDB 的物理日志，先写日志再改数据页，也就是 WAL，崩溃后靠它恢复，保证持久性；binlog 是 MySQL 服务层的逻辑日志，用于主从复制和按时间点恢复。redo log 和 binlog 之间用两阶段提交，保证两份日志一致。这和幕 8 的强保证是同一个思想：要么都成功，要么都回滚。

079

数据存得对了，接下来是查得快：索引。InnoDB 用 B+ 树：扇出很大，千万级数据通常只有三到四层，磁盘 IO 次数很少；数据只存在叶子节点，叶子之间用链表连起来，范围查询很快。主键索引是聚簇索引，叶子节点存的就是整行数据；二级索引的叶子节点存的是主键，查到主键之后还要回主键索引再查一次，这叫回表。

080

所以索引优化的核心就是：遵守最左前缀原则，联合索引要从最左边的列开始用；尽量用覆盖索引，让要查的列都在索引里，避免回表；不要在索引列上用函数或做隐式类型转换，否则索引会失效。

086

磁盘再快也快不过内存，于是加一层缓存，Redis。它快的原因是：数据全在内存里；命令执行是单线程的，没有锁竞争，6.0 之后网络 IO 可以多线程；网络层用的正是幕 11 讲的 epoll；底层数据结构针对内存做了专门优化。内存有限，所以要有过期和淘汰：过期键靠惰性删除加定期删除，内存满了按策略淘汰，比如 LRU 或 LFU。

084

Redis 常用的结构有 string、hash、list、set、zset。其中 zset 用跳表加哈希表实现，适合排行榜这类场景。有了缓存，就有一致性问题，最常用的是 Cache Aside：先更新数据库，再删除缓存，而不是更新缓存。并发下还可能读到旧值写回缓存，可以用延迟双删，或者订阅 binlog 异步删除缓存。

085

缓存用不好，会出三类问题：穿透，查一个根本不存在的键，每次都打到数据库，用布隆过滤器或者缓存空值解决；击穿，一个热点键过期的瞬间，大量请求同时打到数据库，用互斥锁只让一个请求去重建，或者设置逻辑过期；雪崩，大量键同时过期，或者 Redis 整个挂了，用随机过期时间、集群高可用、限流降级来解决。

083

最后，单台机器会挂，数据要复制到多台，那就要保证多台机器之间一致，这就是 Raft。它把问题拆成三块：选主，用任期号和随机超时，拿到多数票的节点成为 leader；日志复制，leader 把日志发给 follower，多数节点确认后才算提交；安全性，保证已提交的日志不会丢失。Raft 只防节点宕机，不防节点撒谎，也就是不防拜占庭错误。因为数据中心内部的节点是可信的，防拜占庭至少要 3f+1 个节点，代价高得多。
