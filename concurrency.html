00为什么并发难：硬件与共享

难点有两个独立来源：看不见（缓存与重排）和 抢着改（共享可变数据）。后面所有工具都在解决这两件事之一。

起因

每个核有自己的 L1/L2；写入先进写缓冲，编译器和 CPU 还会重排指令。都是为了快。

问题

你写 data=42; ready=true;，另一个核可能先看到 ready，此时 data 还是 0。

问题

同进程线程共享堆、全局、fd。++counter 是「读-改-写」三步，交错执行就会丢更新。

结论

C++ 里这叫 数据竞争 = 未定义行为。不是「结果偶尔小一点」，而是整个程序行为不受保证。

线程共享什么 / 私有什么

共享（一个进程一份）私有（每条线程一份）
堆内存、全局与静态变量、代码、打开的文件与 socket 栈（局部变量）、寄存器、当前执行位置、线程 ID
推论：要加锁的正是「共享 且 可变」的东西。线程自己栈上的局部变量不用锁；创建线程前就固定、之后只读的数据也不用锁。

硬件不是完全放任：MESI

各核改自己缓存，但有缓存一致性协议：谁要写，就广播让别人那条 cache line 失效；别人再读时去拿最新值。所以同一个地址最终会一致。

但它不管：两个不同变量的可见顺序。data 和 ready 可能在不同 cache line，各自同步各自的。这正是内存序要解决的（见 §5）。
核 (core)真正执行指令的硬件。线程必须被调度到核上才在跑。
缓存行 64B缓存按行管理。两个变量挤在同一行，会互相拖累 → False Sharing。
进程 vs 线程进程是资源容器，线程是执行流。进程退出，它的线程全部终止，detach 也救不了。

01先有执行流：std::thread 与生命周期

要并发，先得有第二条执行流。这一节唯一的坑是生命周期：C++ 强制你显式了结每一条线程。

起因

直接调 work() 是当前线程顺序执行；std::thread t(work) 是另开一条，构造完立刻开始跑。

问题

对象析构时若还 joinable，直接 std::terminate()。而且跑完也不会自动变成非 joinable。

解法

析构前必须 join()（等它结束）或 detach()（放手不管），二选一。

新代价

detach 后线程可能引用已销毁的局部变量；thread 本身不是完整 RAII。→ C++20 jthread。

joinable 的真正含义

不是「线程还在跑」，而是「这个对象还关联着一条未了结的线程」。了结 = 你调用过 join 或 detach。

状态joinable
std::thread t; 默认构造false（空壳）
std::thread t(work); 刚创建true
线程函数已经 return，但没 jointrue ← 最容易错
join / detach 之后false
被 std::move 走之后的原对象false
// join 之后：真实线程结束，对象还在，只是变成空句柄
std::thread t(work);
t.join();          // 阻塞等待 + 切断关联
t.joinable();      // false；再 join 会抛 system_error

// 传引用必须 std::ref，否则改的是副本
std::thread t2(inc, std::ref(n));

// 成员函数：要带上对象
std::thread t3(&Foo::run, &foo, 42);
三条铁律：① 每个 joinable 的 thread 必须 join 或 detach；② 操作前先判 joinable()；③ 有 C++20 就优先 std::jthread（析构自动 join，还支持 stop_token 协作取消）。

底层：pthread

Linux 上 std::thread 通常封装 pthread_create。POSIX 版本更 C：入口必须是 void*(void*)，所以要 extern "C" 包一层，再用唯一的 void* data 把 this 传进去。

extern "C" void* entry(void* data) {
    return static_cast<Handler*>(data)->receiveRequest();
}
pthread_create(&tid, &attr, entry, this);   // ≈ std::thread t(entry, this)
pthread_join(tid, nullptr);                 // ≈ t.join()
pthread 不会因为没 join 就 terminate——那是 std::thread 析构函数的规定。pthread 没 join 只是资源没回收。

02正确性第一步：互斥 mutex

有了共享数据和多条执行流，就必须让「同一时刻只有一个人改」。

起因

++counter 在 CPU 上是读→加→写三步，两条线程交错就会丢更新。

解法

std::mutex：一个共享对象。同一时刻只有一个线程能持有它，其余调用 lock() 的线程阻塞等待。

问题

手写 lock()/unlock()，中途 return 或抛异常就漏了解锁，别人永远死等。

解法

RAII 包装：lock_guard 构造加锁、析构解锁，异常路径也安全。

常见误解：不是「只有一个线程能调用 lock」，而是「同一时刻只有一个能持有」。每个要碰共享数据的线程都会写 lock，只是排队。

锁放哪：和被保护的数据成对

class ServiceList {
    std::mutex mtx_;                 // 锁
    std::map<K,V> data_;             // 被它保护的数据
public:
    void update(...) {
        std::lock_guard<std::mutex> lk(mtx_);
        // 约定：碰 data_ 必须先拿到 mtx_
    }
};
放法评价
类成员（最常见）✅ 锁和数据同生命周期，不会拿错锁
全局 / 静态✅ 仅当数据确实是进程级唯一一份
函数内局部变量❌ 每次调用一把新锁，等于没锁
一把锁可以保护多份数据。判断标准：这几份数据是不是「总是一起改」。是 → 一把；彼此独立且是热点 → 各一把（但要小心死锁）。

三种 RAII 包装怎么选

lock_guard11unique_lock11scoped_lock17
构造加锁 / 析构解锁是默认是是
中途 unlock / 再 lock不能能不能
defer_lock / try_to_lock不能能—
配 condition_variable不能必须用它不能
一次锁多把、防死锁不能不能能
日常建议默认用它需要灵活时要拿两把锁时
unique_lock 手动 unlock() 后再 lock()，不需要自己收尾：析构只看「此刻还持不持有」，持有就解，不持有就什么都不做。

锁的家族

类型核心语义适用
mutex一次一人，拿不到就睡默认选择
recursive_mutex同线程可重复加，加几次解几次能避免就避免（常是设计不顺）

03不要空转：条件变量

mutex 解决了「别同时改」，但解决不了「队列空了怎么办」——总不能拿着锁 while 空转。

起因

消费者要等「队列非空」。忙等浪费 CPU；反复 lock 看一眼再 unlock 也笨。

解法

condition_variable：条件不满足就睡（不占 CPU），别人改好条件后 notify 叫醒。

问题

wait 时必须能临时放开锁（否则别人没法改条件），所以只能传 unique_lock，不能是 lock_guard。

新代价

存在虚假唤醒：没人 notify 也可能醒。所以必须带谓词，醒来重新检查。

三件套永远绑在一起

共享数据queue / bool ready——条件本身就是共享的
一把 mutex保护这份数据；一个 cv 只能配一把 mutex，混用是 UB
condition_variable在这份数据上「等 / 叫醒」
// 等待方
std::unique_lock<std::mutex> lk(mtx);
cv.wait(lk, []{ return !q.empty(); });
// 返回时保证：① 你持有锁 ② 谓词为 true
int x = q.front(); q.pop();

// 通知方：先在锁里改条件，再 notify
{ std::lock_guard<std::mutex> lk(mtx); q.push(42); }
cv.notify_one();

wait 内部到底做了什么

持有锁 → 检查谓词
   为假 → 原子地：解锁 + 睡眠      ← 原子性防止「丢失唤醒」
   被叫醒（notify 或虚假唤醒）
        → 先重新抢锁（可能还要排队）
        → 拿到锁后再检查谓词
             假 → 继续睡
             真 → wait 返回（你已持有锁）
顺序别记反：是「先抢锁，再看条件」，不是「先看条件再抢锁」。另外，重新拿锁的是被唤醒的线程自己，不是 notify 干的。
为什么虚假唤醒是被允许的？
① 底层常用 futex / LL-SC，严格保证「绝不多醒、又绝不漏醒」会让实现更复杂更慢；多醒一次的代价只是再判断一下，漏醒一次可能永久卡死，所以实现宁愿多醒。
② notify_all 后大家抢锁，先拿到的人可能已经把数据取走，后来者醒了发现条件又变假（严格说这是「过时唤醒」，处理方式相同）。
③ POSIX 的 pthread_cond_wait 从一开始就不保证，C++ 沿用该模型。
结论：永远写 wait(lk, pred)，等价于 while(!pred()) wait(lk);
没有谓词就不需要锁了吧？（不对）
锁有两个作用：保护条件数据 + 保证 wait/notify 的衔接。没有锁会出现丢失唤醒：
等待方：检查完发现是空的 → （此刻）通知方 notify → 等待方才睡下去 → 这次 notify 丢了，永远醒不来。
有锁时 wait 内部「解锁+睡眠」是原子的，通知方必须先拿到同一把锁才能改条件，所以不会插进这个缝隙。不写 lambda 只是把条件检查挪到外面，不等于没有共享、更不等于可以不锁。
notify_onenotify_all
叫醒一个等待者全部等待者
用在一个人就能处理完（入队一个任务）所有人都需重新判断（stop 关停、容量变化）
没人在 wait 时调 notify，这次唤醒直接丢弃，不会存起来给后来者。所以顺序必须是：先在锁里改条件，再 notify——晚到的 wait 会自己看到条件已为真，不会睡。

04用锁的代价：死锁

锁解决了竞争，却引入新故障：大家互相等，程序还活着但不再前进。

四个必要条件（同时成立才死锁）

条件含义怎么破
互斥资源一次只能一人用用不可变数据 / 每线程一份（多数时候破不了，也不必破）
占有且等待手里拿着锁，还要下一把不嵌套加锁；要拿就一次拿齐
不可剥夺不能抢别人的锁，只能等他放try_lock 失败就释放已有锁重试（注意活锁，需退避）
循环等待A 等 B，B 等 A 成环统一加锁顺序 / std::scoped_lock(a,b) ← 最常用
// ❌ 交叉加锁：线程1 持 a 等 b，线程2 持 b 等 a
{ std::lock_guard l1(a); std::lock_guard l2(b); }   // 线程1
{ std::lock_guard l1(b); std::lock_guard l2(a); }   // 线程2

// ✅ 一次性拿齐，标准库负责避免成环
std::scoped_lock lk(a, b);
最实用的一条经验：持锁时默认不要再去 lock 第二把，也不要调用「里面可能加锁」的函数。临界区只改数据、尽量短。

死锁之外的近亲

活锁都在动、都在重试，却谁也推进不了。try_lock 互相谦让时常见 → 加随机退避。
饥饿某线程一直抢不到锁。读写锁里「写饥饿」典型：读者络绎不绝，写者永远等不到。
自死锁同一线程对非递归 mutex 再 lock 一次，等自己 unlock，永远等不到。

05另一条路：原子性与内存序

锁太重、或只改一个变量时，用 atomic。但要区分清楚三件不同的事。

原子性 Atomicity这一次操作不可分割，别人看不到做到一半。
可见性 Visibility我改完了，别的核什么时候能看到。
有序性 Ordering两笔写入，对面会不会颠倒看到。
三者互相独立：可以「原子但暂时不可见」（还在写缓冲里）；也可以「每次读写都原子，但两次 store 的顺序仍乱」。所以有了 atomic 还要选内存序。

std::atomic

std::atomic<T> 是类模板；原子操作是发生在它上面的那次读写。T 必须平凡可拷贝（trivially copyable，能当纯字节搬），所以 atomic<string>、atomic<vector> 不行。

std::atomic<int> c{0};
c.fetch_add(1);            // 原子 +1
c.load(); c.store(5); c.exchange(9);
c.compare_exchange_weak(expected, desired);   // CAS

六种内存序

序保证什么用在
relaxed只保证本变量原子，不同步周围任何内存纯计数器（不靠它读别的数据）
consume实践中基本不用，多按 acquire 处理—
acquire读：看到旗标后，之后的读能看到对方 release 前的写入读旗标
release写：这之前的写入，对看到该旗标的人可见发布数据
acq_rel读改写（如 fetch_add）同时具备两者RMW 操作
seq_cst全局一个总顺序，不写就是它（默认，最强最好懂）拿不准时
// 经典发布 / 获取配对
data = 42;                                        // 普通写
ready.store(true, std::memory_order_release);     // 发布

if (ready.load(std::memory_order_acquire))        // 获取
    use(data);                                    // 保证看到 42
内存序打在单个原子操作上，作用却不限于它自己。relaxed 基本只管本变量；acquire/release 是拿这一个原子变量当挂钩，去同步旁边一堆普通变量。
既然 relaxed 也是原子的，为什么还要它？
六种序都保证原子性，差别只在要不要额外的同步。更强的序要插内存屏障（冲写缓冲、拦重排），是有成本的。纯统计计数 hits.fetch_add(1, relaxed) 不需要「看到计数就等于看到旁边数据」，用默认 seq_cst 只是白交同步税。但一旦拿它当旗标发布数据，relaxed 就会出错。
atomic + 内存序 = mutex 吗？（不是）
mutex ≈ 互斥 + 一套够强的内存序（lock≈acquire，unlock≈release）。
atomic + 内存序 = 单变量原子 + 你选的可见性，没有「这段代码请排队」。
发布模式只保证「看到 ready 的人能看到 data」，但两个人仍可能同时执行 use(data)。要保护「先改 map 再改 size」这种多步不变量，只能用锁。

fence

std::atomic_thread_fence(order) 是独立屏障：不绑定任何变量、不改数据，只在当前线程插一道顺序栅栏。应用代码很少直接用，优先写 store(release) / load(acquire)。它不提供互斥，替代不了锁。

06更进一步：无锁编程

锁会让线程睡；持锁者被换下时别人全等着。无锁用「原子地换一版状态，失败就重来」代替阻塞。

起因

希望某线程卡住时，其他线程仍能推进（lock-free 的定义），并减少上下文切换。

解法

CAS 循环：load 当前值 → 本地算好完整新状态 → compare_exchange 装上去 → 失败按最新值重算。

问题

CAS 只比较比特：值 A→B→A 变回来了，它以为没人动过 → ABA。

新代价

摘下的节点不能立刻 delete（可能还有人捏着旧指针）→ 需要安全回收协议。

CAS：weak vs strong

std::atomic<Node*> head{nullptr};
void push(Node* n) {
    Node* old = head.load();
    do { n->next = old; }
    while (!head.compare_exchange_weak(old, n));   // 失败时 old 已被更新成最新值
}
compare_exchange_strongcompare_exchange_weak
失败原因基本只有「值真的变了」值变了 或 假失败
必须循环？否，可以只试一次是，不循环会把假失败误判成「别人改了」
为何有假失败—有的 CPU 用 LL/SC，中断或缓存行被碰就会 SC 失败

ABA 与安全回收：两个不同的问题

方案解决核心判断
tagged pointerABA（认错代）指针 + 版本号打成一个字一起 CAS。地址复用了但 tag 变了 → CAS 失败
Hazard Pointer过早释放读者把正在用的指针写进自己的槽；回收者扫描所有槽，不在里面才 delete
RCU过早释放读者进出很轻的读临界区；写者摘节点后等这一波读者全部离开再 delete
Epoch过早释放读者登记当前世代号；写者等到没人再停在那一代才 delete
Hazard 是按指针点名保护；RCU / Epoch 是按时间波次回收（等这班车的人都下车再拆车）。谁负责回收？逻辑摘除和最终 delete 都是写者做，读者只负责「报到」。

SPSC：用角色分工省掉 CAS

SPSC 是一种约束（Single Producer Single Consumer），不是标准库的类。常做成环形数组：

生产者只改 tail，消费者只改 head，两人写的不是同一个变量
push: 写槽位 → tail.store(next, release)     // 先写数据，再发布下标
pop : tail.load(acquire) → 读槽位 → head.store(..., release)
空: head==tail    满: (tail+1)%Cap==head     // 浪费一个槽区分
alignas(64) 隔开 head/tail                    // 避免 False Sharing
因为没有两个写者去改同一个原子变量，不需要 CAS，load/store + acquire/release 就够。固定数组也没有链表那种回收难题。MPMC 则两端都要 CAS，还要处理 ABA。
无锁不一定更快。CAS 重试、缓存行来回弹（cache line bouncing）都可能比一把锁更慢，而且难写对。先写对有锁版本，测出锁是热点，再把那个很小的共享点改成原子。

07换个视角：从「线程」到「任务」

前面都在解决正确性。接下来是组织问题：std::thread 的第一个不便是——拿不到返回值。

问题

std::thread t(work) 里 work 的 return 值丢了；线程里抛出的异常会直接 terminate。

解法

std::future：取结果的那一头。get() 会阻塞等待，异常也会在 get() 时重新抛出。

三种生产者

往 future 里送结果的方式：promise（手动）、packaged_task（函数 return）、async（连跑带送）。

四者的关系（面试主线）

thread          → 我要一条执行流（与 future 无绑定，所以拿不到返回值）
future          → 我要一个结果（get 会等；只能取一次）

promise         → 最底层的「管子」。不开线程，谁算完谁 set_value / set_exception
packaged_task   → 函数 + 内部 promise。不开线程，你调用它，return 值自动进 future
async           → 打包任务，并且按策略可能替你开线程，直接给你 future

依赖关系：
   async ≈ 可能开 thread + packaged_task（内含 promise）→ future
   packaged_task = 函数 + promise → future
   promise → future
开线程吗结果怎么产生典型场景
thread是拿不到长期跑的常驻线程
promise否手动 set_value结果来自回调 / C API / 另一阶段
packaged_task否调用它，函数 return要丢进自己的线程池
async可能自动一次计算要返回值
// promise：通道，线程你自己安排
std::promise<int> p;  auto f = p.get_future();
std::thread t([&p]{ p.set_value(42); });
f.get();  t.join();

// packaged_task：函数 return 自动进 future；只能 move
std::packaged_task<int(int,int)> task(add);
auto f2 = task.get_future();
std::thread t2(std::move(task), 3, 5);
两个必提的坑：
① async 默认策略不保证开新线程（可能 deferred，等 get 时才在当前线程跑）。要并行请显式写 std::launch::async。
② async 返回的 future 析构会阻塞到任务结束。写成临时量 std::async(f1); std::async(f2); 会变成串行——必须把 future 存住。

08复用执行流：线程池

有了任务视角，下一个问题是：来一个任务就 new 一条线程太贵，线程太多还会互相抢核。

起因

线程创建/销毁有开销；短任务多时，开销可能超过任务本身。

解法

任务是短的，线程是长的：预创建 N 条 worker，共享一个任务队列，反复复用。

复用前面所有零件

队列用 mutex 保护，空闲用 cv 睡，结果用 packaged_task + future 带回。

新代价

怎么优雅关闭？工人都睡在 cv 上，直接 join 会卡死，不 join 又会 terminate。

设计要点（口述版）

组件为什么是它
vector<thread> 存工人构造时 emplace_back 就地构造（thread 只能 move）
入口写 [this]{ worker_loop(); }worker_loop 是成员函数，必须靠 this 才能调
queue<function<void()>> 存任务统一成「无参、无返回」的可调用对象，工人只管 job()
mutex 保护队列 + stop多个工人同时 pop、多个线程同时 submit
cv 谓词 stop || !tasks.empty()必须带 stop，否则关池时工人醒来发现队列空又睡回去，join 卡死
锁内取任务，锁外执行否则一个慢任务会一直握着锁，别人既取不了也 submit 不了
void worker_loop() {
  for (;;) {
    std::function<void()> job;
    {   std::unique_lock<std::mutex> lk(mtx_);
        cv_.wait(lk, [this]{ return stop_ || !tasks_.empty(); });
        if (stop_ && tasks_.empty()) return;      // 停了且没剩活，才下班
        job = std::move(tasks_.front());          // move 只搬内容
        tasks_.pop();                             // pop 才删元素
    }
    job();                                        // 锁外执行
  }
}

submit 那两行的三层包装

auto task = std::make_shared<std::packaged_task<R()>>(
        std::bind(std::forward<F>(f), std::forward<Args>(args)...));
tasks_.emplace([task]{ (*task)(); });
① bind把「函数 + 参数」绑成无参可调用对象——队列里只能放 void()，没法再传参。
② packaged_task调用后 return 值 / 异常自动进 future，调用方 get() 就能拿。
③ make_sharedpackaged_task 只能 move，而 std::function 要求内部可拷贝 → 套 shared_ptr，lambda 只拷指针。

优雅关闭：stop 的作用

stop_ = true      ① 让谓词能变真，空队列也允许退出
notify_all()      ② 把睡在 cv 上的工人全叫醒
join() 每条线程   ③ 等它们从 worker_loop return

没有 ① → 工人永远睡，join 卡死
没有 ③ → thread 仍 joinable，析构 terminate
使用约束：不要在任务里同步等待同一个池里尚未执行的任务——工人可能全被占满互相等，死锁。另外无界队列在生产过快时会堆积内存，生产环境需要有界队列 + 背压。

任务取消是协作式的

时机能否取消做法
还在队列里能包一层：执行前先查 token，已取消就抛异常，用户函数根本不跑
已经在跑只能协作任务自己在循环里查 stop_token / atomic<bool>，看到就 return
C++ 没有安全地强杀线程的手段。future 也没有 cancel()。pthread_cancel 会让析构、锁、内存都处于未定状态，不要用。

09线程池不保序：Strand 与异步 IO

线程池让任务并行，但同一个连接的多个回调并行执行时，会同时改同一份会话状态。

起因

IO 完成通知可能落在任意 worker 上。同一 socket 的两个 handler 可能同时跑。

问题

mutex 能互斥，但不保证顺序——A 先投递不代表 A 先执行。

解法

Strand：同一条 strand 上的任务 FIFO 且绝不并行，像一条逻辑单线程。

收益

一个连接配一把 strand，会话状态在回调里可以像单线程一样写，不必处处加锁。

实现原理：私有队列 + running 标志

post(f):
    加锁 → f 入自己的队列 q_
         → 若 running_ == false: running_=true, 需要启动
    解锁 → 若需要启动: 向线程池 submit 一次 drain

drain(在某一个 worker 上):
    循环: 加锁取队头 → 解锁 → 执行
          队列空 → running_=false, return

关键：已经 running 时只入队，不再 submit
      → 同一时刻只有一个 drain → 保序且不重叠
mutexstrand
互斥✅✅（同一 strand）
顺序❌ 谁抢到算谁✅ 按 post 顺序
写法回调里自己 lock投递时绑定，回调里像单线程
// Asio 风格：把这个连接的所有 handler 绑到同一 strand
auto st = asio::make_strand(io_ctx);
asio::async_read (sock, buf, asio::bind_executor(st, on_read));
asio::async_write(sock, buf, asio::bind_executor(st, on_write));
「与 IO 绑定」的含义：不是 strand 去做 recv，而是这个 fd 上的完成通知都进同一条保序队列。等网卡仍可在多个核上并行，不同连接用不同 strand 也仍然并行。
strand 保的是「handler 串行」，不是「先发起的 IO 先完成」。另外，在 strand 回调里同步等待同一条 strand 上后面的任务 = 自死锁。IO 回调应当短，只负责 post 下一步。

再往前一步

事件循环 Reactorepoll 等就绪 → 回调。少量线程扛大量连接。
协程 C++20co_await 让「等 IO」不占线程，写起来像同步，跑起来是异步。
线程数选择CPU 密集 ≈ 核数；IO 密集可多于核数（大部分时间在等）。

10最后：怎么证明它是对的

并发 bug 是概率性的。「跑了没崩」不构成正确性证据。

ThreadSanitizer-fsanitize=thread。运行期检测数据竞争，最有效的工具，优先上。
死锁现场gdb thread apply all bt / pstack，看谁卡在 lock 上、等谁的锁。
perf看上下文切换、cache-misses、锁争用。判断是不是 False Sharing。
Amdahl 定律串行部分决定加速上限。加线程不一定更快，先量再改。
优化顺序：① 先写对（mutex + cv，简单直白）→ ② 测出热点 → ③ 缩小临界区 / 拆锁 / 分片 → ④ 单变量换 atomic → ⑤ 最后才考虑无锁结构。跳步很容易得到「又慢又错」。

◆面试高频追问

线程跑完了，joinable 会自动变 false 吗？
不会。线程函数 return 后仍是 joinable（类似僵尸状态，等人回收）。变 false 只有四种：join、detach、被 move 走、默认构造的空对象。所以「已经跑完但没 join」，析构照样 terminate。
只有 join 才能避免 terminate 吗？
不是，detach 也可以——它同样让对象变成非 joinable。准确说法是：析构时若仍 joinable 就 terminate，与线程跑没跑完无关。另外这条规则只属于 std::thread；pthread_t 没 join 不会 terminate，只是资源未回收。
main 返回后，detach 的线程还能跑完吗？
不能。线程依附于进程，进程退出，它的线程全部终止，而且通常不是让它干净地 return——剩余代码不会跑、栈上对象不保证析构。要保证跑完，就不能让进程先退出，得 join。
为什么 cv.wait 不能用 lock_guard？
wait 内部要「原子地解锁 + 睡眠」，醒来再加锁。lock_guard 锁到作用域结束，中途不能解锁，所以只能用 unique_lock。这是 cv 的要求；unique_lock<T> 本身的 T 可以是各种锁类型，只是配 condition_variable 时必须是 std::mutex（其他锁要用 condition_variable_any）。
不传谓词就不需要锁了吧？
仍然需要，而且编译上也强制要传锁。锁不只保护条件数据，还保证 wait 与 notify 的衔接：没有它会出现「检查完是空的 → 对方 notify → 我才睡下」→ 唤醒丢失，永久卡死。
notify 之后，被叫醒的线程立刻开始执行吗？
不是。醒来后先要在 wait 内部重新抢那把 mutex（可能还要排队），拿到锁才检查谓词，为真才从 wait 返回。notify_* 自己不加锁、不改条件、也不帮对方加锁。
一个 condition_variable 能配不同的 mutex 吗？
不能，是未定义行为。同一把 cv 上所有等待者必须用同一把 mutex。三件套（共享条件 / mutex / cv）永远绑定在一起。
atomic 加上内存序，是不是就等于 mutex？
不是。mutex ≈ 互斥 + 足够强的内存序；atomic + 内存序只有「单变量原子 + 可见性」，没有互斥——两个线程仍可能同时执行同一段逻辑。多步不变量（改 map 再改 size）必须用锁。
内存序是只针对单个变量吗？
参数打在某一次原子操作上，但作用不限于它：relaxed 基本只管自己；acquire/release 是拿这个原子变量当挂钩，去同步旁边一堆普通变量的可见性。
为什么 compare_exchange_weak 必须放循环里？
它允许假失败（值没变也可能失败，源于 LL/SC 实现）。不循环就会把假失败误当成「别人改了」而走错分支。只试一次、失败要走别的逻辑时，必须用 strong。
无锁一定比 mutex 快吗？
不一定。CAS 重试、多核打同一缓存行的 bouncing 都可能更慢，而且正确性难保证（ABA、回收）。lock-free 的价值是「进展性保证」——某线程卡住时别人仍能推进，不是无条件更快。
std::async 和线程池的区别？
async 是一次性任务，实现不保证复用线程，默认策略甚至可能 deferred；线程池是固定工人消化大量短任务，调度权在你。另外 async 的 future 析构会阻塞，容易把并行写成串行。
线程池怎么优雅退出？
① 加锁置 stop_=true；② notify_all 叫醒所有睡着的工人；③ 工人发现 stop && 队列空 才 return（已入队的任务先做完）；④ 对每个 joinable 的 thread 调 join。缺 ① 会 join 卡死，缺 ④ 会 terminate。
strand 和 mutex 到底差在哪？
两者都能互斥，但 mutex 不保证顺序，strand 保证按 post 顺序执行且绝不重叠。strand 还让回调代码可以「像单线程一样写」，省掉散落各处的锁。代价是同一 strand 上失去并行。
